# 0.4.0：预览与导出色差、原软件整机对照

本轮先定位色差，再修改生产代码，最后以同源素材检验原剪映与映序。原软件为本机剪映专业版 11.4.1.14443，复现程序为独立实现的映序剪辑 0.4.0。完整验收状态与数值以附带 JSON 为准；报告不把局部颜色实验称为全软件等价证明。

## 原因及证据层次

旧色卡生成命令虽然指定了 BT.709，实际 H.264 SPS 却只有矩阵为 709，原色与传递函数为未指定。浏览器对这份不完整描述采用了 601，而 FFmpeg 按矩阵采用 709。保持解码 YUV 不变、仅修复 SPS 的受控实验能消除明显偏色，因此主因是输入解释不一致，不是简单给亮度加一个补偿值。

旧预览的零调色状态直接显示 video，启用调色后才进入 Canvas。完整 601 视频在两条显示路径上也可能发生不同处理，造成切换时的色差。显示器 ICC 还会改变实际截图的 RGB，不能把显示器空间的截屏直接与文件工作 RGB 当成同一色彩域比较。多轨测试进一步证实：各个 DOM 图层分别经过 ICC 后再混合，与导出先混合工作 RGB 的顺序不同。对齐实际帧 PTS 后，默认 ICC 的混合误差达到 12；仅用于定位的 sRGB 控制实验降为 3，锁定了混合与显示转换不交换这一原因。

原软件安装文件里的 NV12 GLSL 清楚区分范围归一化、YUV 矩阵和 HDR 分支；受控原着色器执行显示，矩阵错配可造成最大 58/255、范围错配最大 21/255 的误差。这里是原组件的因果实验，不等于当前 GUI 运行时选择已被证明。

随后实际启动原剪映，用自制 32 色卡新建工程，完成图片默认、图片亮度 +20、完整 709 视频和完整 601 视频的预览与 MP4 导出。709 与 601 都保留编码 RGB 的显示数值。该整机证据纠正了中间“严格源 transfer 转 sRGB”的方案：严格转换会使暗部 20 变为约 36，虽然可让映序内部一致，却与被复现软件不同。

调色控件还发现另一项差异：原 GUI 亮度、对比度、饱和度都钳制在 −50 至 50。旧映序按 −100 至 100 显示，导致同样填写 20 时强度减半。底层归一化公式可以保留，界面应按显示值／50 换算。

## 最终实现

- 保留原素材及原始色彩事实，采用经整机样例验证的 SDR 显示兼容解释；真正转换矩阵与范围，保留编码 RGB 的显示亮度，不额外套用源 SDR 原色／gamma 变换。
- 视频预览代理和导出采用完整 BT.709 矩阵／原色、sRGB transfer=13、全范围标签。颜色变换与写入标签分开处理，输出经探测校验；它与剪映默认有限范围 709／709／709 标签策略不同。
- 所有预览帧共用 Canvas 调色路径，包含三个参数为零时。裁剪、镜像、位置、旋转、缩放、透明度和转场在一个 sRGB 画布中按轨道顺序合成，再进行一次显示器颜色处理。系统 ICC 保留；同显示空间的回看截图与工作 RGB 数值分别检验。
- 视频音轨继续来自原文件，画面代理不携带重新编码的音轨。原声与代理画面同步，音量、淡入淡出及转场增益只应用一次。
- 缓存按源路径、大小、修改时间、色彩规则版本失效，临时写入完成后才发布；导入可显示进度和取消，重开工程逐项准备，避免同时启动大量编码任务。工程只保存原素材相对路径。
- 修复已在工作空间的视频重新导入时触发的 FFmpeg identity 分支异常；奇数尺寸先扩展到偶数参与转换，再恢复精确原尺寸，以 4:4:4 代理保存。
- 三项调色界面量程改为 ±50；旧工程保存的归一化值不变。最终导出质量由原 CRF 20 改为 CRF 18，编码损失减少单独记账，不把所有误差改善都归因于元数据修复。

## 验收安排与阅读方式

模型、媒体、协议和本地语音识别使用真实 Node 测试；桌面流程检验多视频轨、两种转场、线性关键帧、自动字幕、裁剪镜像、调色、音量包络、撤销重做、保存重开、导出及重新导入。

颜色闭环采用明确标签的 601／709／全范围／缺字段素材，既比较 Canvas 工作 RGB 与 FFmpeg 解码成品，也在同一实际窗口回看导出视频。原应用对照另用相同 32 色素材，分别量化两个程序的实际成片。所有色块采样均避开 4:2:0 边界；不通过改参考或放宽阈值掩盖失败。

可直接打开项目 `outputs/0.4.0-色彩与整机对比.html` 查看原程序与映序的成片、截图和采样表。最终交付记录为 `outputs/final-acceptance-v0.4.0.json`。随包离线材料位于本目录 `evidence/phase6/`，完整实验与失败复现保留在正式项目的 `outputs/`、`work/` 以及研究目录中。

## 明确边界

本轮验证范围为本机 SDR 601／709 视频、受测 sRGB 图片与合成短片。HDR、杜比视界、任意图片 ICC／广色域管理、长片压力及跨机器验证未完成。检测到不支持的 HDR／广色域描述时拒绝误处理；完全缺失的标签只能按公开写出的默认规则解释，不能恢复拍摄意图。

原软件整机对照覆盖上述四类场景和九组 GUI 调色采样；多轨、转场、关键帧、自动字幕等核心流程在映序中做了实际桌面与媒体回归，但不能据此声称每个功能都与原软件逐帧一致。复杂特效、模板、蒙版、缓动、曲线变速和其它 AI 功能尚未复现。旧版的原 shader 组件对照与本轮 GUI 整机对照是不同证据层次。

## 可复查来源

本地原应用证据：研究项目 `outputs/phase6-gui/original-gui-comparison.json` 与 `gui-color-samples.json`；原资源、偏移、哈希、反编译及隔离执行详见 `outputs/phase6-color-findings.json`、`phase6-brightness-mapping.json`。

[FFmpeg colorspace 官方文档](https://ffmpeg.org/ffmpeg-filters.html#colorspace)说明输入／输出矩阵、原色、传递函数和范围的独立控制；[setparams 官方文档](https://ffmpeg.org/ffmpeg-filters.html#setparams)说明它仅设置帧属性，不能代替真正像素转换。产品结论以本机实测为依据，不把公开主干源码的行为直接等同于当前安装版本。

两程序实际窗口截图仍有显示管理差异：本机跨程序截图最大通道差为62/255，此结果原样保留，未用“色差已修复”覆盖。它不属于同一工作RGB的文件比较，也没有被声明为已实现全局屏幕逐像素一致。本轮修复保证的是受测映序预览／导出链及上述同源成片的数值一致范围。

缺标签的旧色卡失败、严格transfer中间方案、ICC多DOM混合失败和force-sRGB控制实验均保留在原实验目录；最后交付采用默认显示管理，没有使用强制sRGB启动开关。独立程序的 `对比验证/` 目录也附带可直接打开的对比页与成片附件。
